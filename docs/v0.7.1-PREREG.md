# v0.7.1 release run: pre-registration (2026-10-22)

Written and committed before the run. v0.7.1 is v0.7.0 plus gate Amendments 17–19 (already on main), one merge, and a version bump.
- **`natevick/mac-metal` (tip 8d64ee3):** S47b.
  - The macOS build draws with wgpu on Metal. Linux keeps glow with the same eframe features as before, and `scripts/macos/check-renderer.sh` fails if that split drifts.
  - `fastframe_text::detect()` moves off the startup path. It made blocking desktop-portal D-Bus calls, up to about 4 s when the portal never answered. Startup now applies the platform default, and a background thread applies the detected settings when they arrive. This is the only change that reaches Linux.
  - Credentials' file backend is built only where it can be constructed (`Backend::File` cfg gate).
  - The Mac budget in `docs/budget.md`, and `docs/s47b-PREREG.md` with its RESULTS.
  - The merge conflicted with nothing.
- **Version:** `crates/app` 0.7.1, a patch bump for a memory fix (macOS) and a startup-stall fix (all platforms), and `Cargo.lock`. `git diff --stat 4cc9f08 -- crates/engine` is empty, so `bramley-engine` stays at 0.3.0 and nothing is published to crates.io.

The integration branch is `natevick/v0.7.1`.

## The run
`scripts/acceptance.sh v071-counted-1`, counted mode, from a clean tree, at the commit that last changed this file (`git log -1 --format=%H -- docs/v0.7.1-PREREG.md`). The harness windows are 1100x720 and 800x600.

## Pass
- The gate PASSes under `docs/acceptance.md` and `docs/s13-acceptance-PREREG.md` Amendments 4–19.
- Amendment 19's one stop rule applies: two consecutive counted runs of the same release that both end VOID, for any cause or mix of causes, stop the re-runs, and the decision goes to Nate. A PASS or a FAIL in between resets the count.
- `realStateUnchanged` is true, and the leak grep is clean.
- `~/.cache/bramley` does not exist after the run. Check by hand.

## What changed for Linux
- Only the text-detect move. Startup no longer blocks on the portal. The renderer, the eframe features, and every engine path are unchanged.
- R1–R6 are expected to be unchanged. The comparison is v0.7.0's R1: 157.2 MiB USS in `v070-counted-1` and 152.4 in `v070-counted-2` (`docs/v0.7.0-RESULTS.md`). The RESULTS file reports the delta against both.
- The background detect thread is short-lived, so it should not move R1. A rise outside the spread of those two readings is reported, even if R1 passes.

## Check by hand
- **No cache left behind.** `~/.cache/bramley` does not exist after the run.
- **No host theme.** The acceptance sessions must not read the host's Omarchy theme. The isolation is `XDG_STATE_HOME` set to `<session config dir>/state`, so the app looks for `<config>/state/omarchy/current/theme/colors.toml`, which does not exist. The run's status files carry no theme field, and the app logs nothing when a theme loads, so the check reads these:
  - **Launch guard.** Every session's `<name>.log` and `<name>.status.json` sit in `target/acceptance/v071-counted-1/`, and each was launched through `assert_isolated`. The verdict's `phaseErrors` is empty and no log or phase error contains `host Omarchy theme could leak`.
  - **Logs.** `grep -il omarchy target/acceptance/v071-counted-1/*.log` finds nothing.
  - **Screenshots.** Before the run, `ls ~/.local/state/omarchy/current/theme/colors.toml`. If it exists, `target/screens/PRIVATE-real-art/acceptance/v071-counted-1/*.png` must not use its `background` colour for the window. If it is absent, say so in the result: the launch guard is then the only evidence.
