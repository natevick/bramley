# Product decisions

- **2026-10-10: developer token distribution (Nate).**
  - A scheduled GitHub Action mints a MusicKit developer token from Nate's key and publishes it as a static file the app downloads. The key lives only as GitHub repository secrets.
  - The app caches the token, refreshes it when fewer than 30 days remain, and keeps working on the cached copy if the fetch fails.
  - No server and no re-release for expiry. Users never see the key.
  - Risk accepted: all Bramley traffic is attributed to Nate's developer account, and Apple can revoke the key.
- **2026-10-10: layout (Nate).** Spotifast's shape:
  - a library sidebar on the left;
  - a content area for search, playlists and albums;
  - a player bar along the bottom;
  - the queue as a side panel.
  Every UI slice ships screenshots before merge.
- **2026-10-10: artwork cache (Nate).** Artwork is cached in memory only, never on disk. Superseded 2026-10-18, below.
- **2026-10-10: agent access (Nate).** Bramley is controllable by agents: a CLI (`bramley play|pause|next|…`) and a local MCP server (`bramley mcp`). Both talk to the running instance. See the compliance interpretation log.
- **2026-10-10: user-token storage (coordinator's call after the S3 review; Nate may override).**
  - The keyring is the source of truth, and there is only ever one copy. An import into the keyring is read back and then deletes the old `music-user-token` file. A save to the keyring also removes the file.
  - The 0600 file is used only when no Secret Service exists on the bus. It is written atomically, and the storage mode ("keyring" or "file") shows in status and the UI. A keyring error, timeout or cancelled unlock prompt is an error, never a silent fallback. A failed keyring write makes the sign-in page show the error instead of "Done".
- **2026-10-10: the sign-in page wipes its own storage (coordinator's call; the reviewer asked for Nate's read under compliance rule 2).** After a successful token POST, the page calls `localStorage.clear()` and `sessionStorage.clear()` on its own loopback origin, and the response carries `Clear-Site-Data: "storage"`. This is our page's behaviour on our origin, not a change to MusicKit. `unauthorize()` is not called, because it would revoke the token Bramley just stored.
- **2026-10-14: the sign-in page sends its origin as referrer (S19, coordinator's call).**
  - The page uses `Referrer-Policy: strict-origin-when-cross-origin`, not `no-referrer`. Under `no-referrer`, Apple's authorize popup issued a music user token but never handed it back, and MusicKit's `authorize()` failed with AUTHORIZATION_ERROR "Unauthorized".
  - The evidence is an A/B on Nate's laptop, one sign-in each: the same page without the header authorized, and with it, it failed. The in-app sign-in then succeeded on the fixed build.
  - Only the origin goes to Apple. The secret path never appears in a Referer header, and MusicKit's own `referrer` query parameter already carried the full URL under `no-referrer`.
  - Don't "harden" this back to `no-referrer`: the header test pins it.
- **2026-10-14: v0.1.2 ships over a failed acceptance check (Nate).**
  - `v012-counted-1` FAILed one check, R3: position lagged the wall clock by 1.06 s. The cause is a slow seek (S22): one 500.79 s library item takes about 5 s to land a seek. It is pre-existing, with the same signature in v1-3, the S15c soaks and the S17 soaks.
  - Three isolated probes could not reproduce it. It shows only inside a full R3 session.
  - Holding v0.1.2 kept S17's position fix from users. On v0.1.1 the song time pins to the end from the second song of a seamless queue on.
  - v0.1.2 ships with the slow seek recorded as a known issue. S22 continues on `natevick/s22-seek-probe`, and the pre-registered next step is a 30-minute trace run.
- **2026-10-16: the sidebar no longer shows where the sign-in is stored (Nate).**
  - Nate, during the 2026-10-16 feedback session: "we don't really care where the credentials are stored." The footer now reads "Signed in to Apple Music" with a Sign out button.
  - This amends the 2026-10-10 user-token storage decision. The storage mode ("keyring" or "file") still shows in the status file as `tokenStorage`, but no longer in the UI. Keyring errors still surface through the notice line.
  - Apple's documented Apple Music API has no endpoint that returns the user's name or Apple ID, so the footer cannot say which account is signed in.
- **2026-10-16: 0.2.0 ships over a failed acceptance check (Nate).**
  - `v020-counted-1` FAILed one check, F4: one cold start of five got a transient HTTP 403 from Apple's storefront sign-in check at launch, and Bramley treated it as signed out. See `docs/v0.2.0-RESULTS.md`.
  - The 403 handling predates 0.2.0 and is in every release. 0.2.0's changes (version 0.2.0 for app and engine, `#[non_exhaustive]` public engine enums, type-to-jump matching) don't touch it.
  - 0.2.0 ships with it as a known issue. The fix is next: confirm a storefront 403 before signing the user out.
- **2026-10-18: on-disk cache for artwork and API responses (Nate).**
  - Nate: "we need to add cache so the load of album art etc is not as slow. If I get in trouble with Apple that is fine".
  - This supersedes "2026-10-10: artwork cache (Nate)", which kept artwork in memory only. See the compliance interpretation log for the matching amendments.
  - **Where:** `$XDG_CACHE_HOME/bramley` (default `~/.cache/bramley`), directories 0700, files 0600.
  - **Art:** the encoded image bytes as fetched, keyed by URL including size. Capped at 512 MB with least-recently-used eviction. Kept at sign-out.
  - **API:** browse responses only (library lists and album, playlist and artist track lists), served stale while one background worker refetches. Scoped to the account and wiped at sign-out. Capped at 64 MB. Listening history (recent plays, heavy rotation, replay summaries, recently added) is never cached on disk. Amended 2026-10-21, below.
  - **Unchanged:** compliance rule 6. Nothing from the playback or license path, and nothing musickit.js fetches, is cached.
- **2026-10-19: a cache warmer, `bramley warm` (Nate).**
  - Nate: "this would only be while the app is not running and I was thinking every few minutes. The cache should not go out of date that quickly and can background update while the app is open so the slowness feel just disappears."
  - A systemd user timer (shipped, not enabled) runs `bramley warm` every 5 minutes. While the app is open the existing stale-while-revalidate keeps the cache fresh, and warm exits at once.
  - Order: the four library first pages; later Albums and Playlists pages (list pages refetched after 30 minutes); then each missing or 6 h old track list with its album-route covers; then grid covers. Budget 60 requests a run, API at 1 per second. A 401 or 403 pauses runs until the app starts again; a 429 or 5xx backs off 5 minutes to 1 hour. Results: `docs/s32-warm-RESULTS.md`.
- **2026-10-19: v0.2.1 ships over a failed acceptance check (Nate).**
  - `v021-counted-1` FAILed F7 (one MCP `library_playlists` call returned an error) and F9 (one of five MCP plays stayed silent), both in the same minute of one session. See `docs/v0.2.1-RESULTS.md`.
  - Neither touches v0.2.1's changes. The MCP library path is byte-identical to v0.2.0, which passed. The S28 engine code runs once at boot, before the first play succeeded. Both are first-ever failures in 22 counted runs. Their causes weren't recorded, because `drive.py` drops the error text (S31).
  - v0.2.1 ships the S28 fix for the storefront 403 sign-out, which caused `v020-counted-1`'s F4 failure, and the de-flaked Home retry test. The disk cache follows as its own release.
- **2026-10-20: the cache warmer refreshes once a day (Nate).**
  - Nate: "Yes we should cut that way down. Once a day feels ok for now".
  - On Nate's laptop, warm had made 1,045 requests in 12 hours: 120 runs, every one `complete`. Most were 6-hour track-list refreshes.
  - Library list pages and album and playlist track lists now refresh after 24 hours, down from 30 minutes and 6 hours, so a warm library costs about one refresh of each a day. Art is never re-fetched. While the app is open, stale-while-revalidate still refreshes what you view.
- **2026-10-20: v0.4.2 ships over a failed acceptance gate (Nate).**
  - In `v042-counted-1` all 16 checks PASSed. The gate was FAIL only because the ballast positive control landed R1's USS at 220.1 MiB, 0.1 MiB outside its 215 ± 5 band. See `docs/v0.4.2-RESULTS.md`.
  - v0.4.2 changes only the warmer's refresh ages, which the app never runs. Nate: "ship it".
  - Follow-up S34: a positive control that misses its band should make a run VOID, not FAIL. To be amended for future runs.
- **2026-10-21: the last Home grid is cached on disk (Nate: "Do both please").**
  - Norm asked whether to cache the last Home grid, which reflects listening. Nate answered "Do both please": cache it, and send Home's ranking requests in parallel.
  - **Amends** the 2026-10-18 cache entry's "listening history is never cached on disk". The final Home grid (album ids in listening order, with their art templates) is now cached. Raw history responses (recent plays, heavy rotation, replay summaries, recently added) still are not.
  - **Where:** the API store, scoped to a hash of the user token, 0600 in a 0700 directory, wiped at sign-out with the API cache.
  - **Behavior:** after the storefront check passes, Home shows the cached grid, ranks live and swaps the grid in one step only if the result differs. `bramley warm` does not refresh it: that needs the history requests warm never makes.
  - Measured in `docs/s39-home-fast-RESULTS.md`: B shows 50 covers in 0.44 s against A's 4.50 s, and parallel ranking alone gets C to 61% of A.
- **2026-10-21: no volume control on macOS (Nate).**
  - Nate: "Nope no slider it is".
  - The macOS 27 SDK's MusicKit swiftinterface has no volume, gain or mute API, and Apple's Music app uses private frameworks.
  - The player bar hides the volume control on macOS, and `bramley volume N` is accepted and does nothing there. Linux is unchanged. See `docs/macos-native-PLAN.md`.
- **2026-10-21: Home's library request goes out with the history requests (Nate accepted).**
  - Home's library request now goes out at the same time as the listening-history requests. It no longer waits to see whether history fills fewer than 50 slots. Follows the parallel ranking in the 2026-10-21 Home-grid entry above (S39, `docs/s39-home-fast-RESULTS.md`).
  - **Cost:** one extra Apple request on each Home load, for accounts whose history alone fills 50. During a 429, each retry round sends one extra request. Rounds back off 5 s, 30 s, then 60 s, and honour Retry-After.
  - **Not exercised by S39:** bar 4 (requests per Home load <= A, measured 9, 9, 9) was measured on an account whose history never fills 50, so it did not exercise this case. `docs/compliance.md` has no request-volume rule for the app.
- **2026-10-21: v0.6.0 ships over a failed acceptance gate (Nate).**

- **2026-10-21: a ballast that only misses its landing band is VOID when the footprint holds (S34).**
  - **Amends** the gate rule that a ballast control that does not hold is FAIL. Both v0.4.2 (220.1 MiB) and v0.6.0 (262.7 MiB) PASSed every check and failed only on where the control landed.
  - **Rule:** if the landing band is the only ballast condition that fails, every check PASSes and the ballast launch's footprint (RSS minus its USS rise) is within 10 MiB of R1's RSS and the pre-ballast USS, corrected for lost sharing, is at or under 200 MiB, the gate is VOID. Otherwise it stays FAIL. Details in `docs/s13-acceptance-PREREG.md` Amendment 17.
  - **Stop rule:** replaced by the single rule in the 2026-10-22 S48 entry below.
  - Applies to runs started at or after commit 3491774.
- **2026-10-22: v0.7.0 ships over a failed acceptance gate (Nate).**

- **2026-10-22: a failed harness Apple call makes a check VOID, not FAIL (S46).**
  - **Amends** the rule that missing evidence is always FAIL. `v070-counted-2` FAILed four checks because the harness's own Apple call got HTTP 403 and aborted the browse phase. Nate: "we need to fix this before future runs".
  - **Rule:** the harness retries 401 and 403 three times. If the call still fails, a check whose only problem is evidence lost to that phase is VOID. Any other missing evidence stays FAIL, and a real FAIL elsewhere still FAILs the gate. Details in `docs/s13-acceptance-PREREG.md` Amendment 18.
  - **Stop rule:** replaced by the single rule in the 2026-10-22 S48 entry below.
  - Applies to runs started at or after commit 512ba41.
- **2026-10-22: R3 reclaim guard and a relative ballast landing (S48, Nate approved).**
  - **Why:** the S45 investigation traced the v0.6.0 and v0.7.0 collapses to a host memory reclaim during R3, and found that v0.7.0's ballast launch holds about 8 MB of kept covers that R1 does not.
  - **Rule:** an R3 PASS is VOID if R3's RSS falls 30 MiB or more during the soak. A FAIL stays FAIL. The ballast lands against its own pre-ballast USS plus its size, ± 5 MiB, not 215. Samples also record `/proc/vmstat` reclaim counters and each process's shared and private split. Details in `docs/s13-acceptance-PREREG.md` Amendment 19.
  - **Stop rule, one for every VOID:** two consecutive counted runs of the same release that both end VOID, for any cause or mix of causes, stop the re-runs and the decision goes to Nate. A PASS or a FAIL in between resets the count.
  - **Guards:** S34's footprint and adjusted-USS guards now apply to every ballast, so a grown baseline cannot pass by landing on its own target.
  - **Replayed:** `v070-counted-1` R3 becomes VOID (RSS fell 72.1 MiB) and its ballast holds. `v070-counted-2`'s ballast holds.
  - Applies to runs started at or after commit 512ba41.
