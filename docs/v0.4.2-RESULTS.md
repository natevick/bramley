# v0.4.2 release run: results (2026-10-20)

## v042-counted-1 at b7373ba: FAIL (the ballast control missed its band)

The run is valid on every did-it-run check in `docs/v0.4.2-PREREG.md`:
- commit b7373ba, the commit that last changed the PREREG;
- clean tree, counted mode;
- 16 of 16 checks present;
- R3 carries 9 landings for 9 seeks (max 2.0 s);
- every session the gate reads recorded `modes` as both off;
- `bin/bramley --version` prints `bramley 0.4.2`;
- `~/.cache/bramley` does not exist after the run.

**All 16 checks PASS.** Real state was unchanged, the leak grep was clean with both planted controls found, and pacing was OK (peak 20, 56 actions).

**The gate is FAIL because the ballast positive control did not hold** (`gate.py:809-810`). The ballast build has to land R1's USS median at 215 ± 5 MiB (`R1_BAR + BALLAST_OVER`, `LANDING_BAND`). It landed at 220.1 MiB, 0.1 MiB outside the band (`landedWithinBand: false`). Every other ballast condition held: one launch, a valid pre-window, the ballast touched, threshold-only, flagged, and the USS rose by the ballast. Earlier counted runs landed between 211.2 and 222.6.

## Cause

The control missed, not the app.
- v0.4.2 changes two constants in `crates/api/src/warm.rs`. Only `bramley warm` uses them; the app never runs that code path.
- A ballast landing 5.1 MiB above target is run-to-run memory variance in the control itself.

## Decision

Under the PREREG, nothing merges on a FAIL. The decision goes to Nate.

Separately, the gate treats a positive control that misses its band as a FAIL rather than a VOID. That makes the run unjudgeable rather than failed. Whether to amend that is S34, for a future run, not this one.
