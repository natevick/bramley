# v0.6.0 release run: pre-registration (2026-10-21)

Written and committed before the run. v0.6.0 is v0.5.0 plus three branches, merged with no conflicts and no behaviour changes of their own:
- **`natevick/theming`:** complete light mode and live Omarchy theming. Theme colours come from one palette, and `~/.local/state/omarchy/current/theme/colors.toml` is re-read about once a second. The acceptance harness now gives every isolated session an empty `XDG_STATE_HOME` inside its config dir, and `assert_isolated` refuses anything else.
- **`natevick/home-fast`:** Home ranking requests go out in parallel, and the last Home grid is cached in the API store (`docs/decisions.md`, 2026-10-21; `docs/s39-home-fast-RESULTS.md`). The gate wipes `art` and `api` from the cache before every launch, so a cached grid cannot reach a gate session.
- **`natevick/macos-native-2`:** the native-MusicKit macOS port. `bramley-engine` gets a default `runtime` feature, and there is a new `crates/macos-player`. On Linux nothing changes, and `scripts/macos/check-no-engine-runtime.sh` passes. There is no volume control on macOS (`docs/decisions.md`, 2026-10-21).

Versions: `crates/app` 0.6.0, a minor bump for a feature. `crates/engine` 0.2.2, a patch bump. For default-feature users the public API and the dependency set are unchanged, so this is a publish of the same API with a new additive feature. That is the only engine change, and `cargo publish -p bramley-engine --dry-run` passes.

The integration branch is `natevick/v0.6.0`.

## Check by hand: no host theme
The acceptance sessions must not read the host's Omarchy theme. The isolation is `XDG_STATE_HOME` set to `<session config dir>/state`, so the app looks for `<config>/state/omarchy/current/theme/colors.toml`, which does not exist. The run's status files carry no theme field, and the app logs nothing when a theme loads, so the check reads these:
- **Launch guard.** Every session's `<name>.log` and `<name>.status.json` sit in `target/acceptance/v060-counted-1/`, and each was launched through `assert_isolated`. The verdict's `phaseErrors` is empty and no log or phase error contains `host Omarchy theme could leak`. A session that would have run with the host's state dir never starts.
- **Logs.** `grep -il omarchy target/acceptance/v060-counted-1/*.log` finds nothing. The app's only theme log line is `omarchy colors.toml is unreadable`, so this catches a theme file that was found but could not be read.
- **Screenshots.** Today the host has no `~/.local/state/omarchy/current/theme/colors.toml`, so a leak would be invisible. Before the run, `ls` that path. If it exists, `target/screens/PRIVATE-real-art/acceptance/v060-counted-1/*.png` must not use its `background` colour for the window. If it is absent, say so in the result: the launch guard is then the only evidence.
